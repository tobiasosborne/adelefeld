# Lane m1-modctx-b: modulus contexts (first part of work package 1.8)

Second attempt at the brief of lane m1-modctx, run in parallel on another model.
Lane directory `lanes/m1-modctx-b/`.  All line references in `src/modctx.c` are the
line numbers at the end of this lane.

## What was done

Every function of `include/adelefeld/modctx.h` except the five `adf_fball` conversions
at the end of the header (lane m1-local owns those) is implemented in `src/modctx.c`:

- `adf_modctx_new_blocks`, `_prime_powers`, `_fmpz`, `_factorial`, `_primorial_pow`
  with the argument validation and the statuses of conventions 5.14 and 3.2.
- `adf_modctx_free`, `adf_modctx_get_modulus`, `_nblocks`, `_block`.
- `adf_modctx_dump_str` (conventions 10.1, body "modctx", lower-case hexadecimal).
- `adf_ctx_desc_init`, `_clear`, `adf_modctx_matches_desc` (conventions 10.2, C2).
- `adf_modctx_new_from_dump`, by hand over `(s, len)`, no NUL terminator and no raw
  input to a FLINT string function; the whole `modctx` text is validated in the order
  of 8.5, then `max_items` is applied to the block count, then the occurrence index.
- The two reduction/recombination kernels `adf_modctx_reduce` and
  `adf_modctx_recombine`.  They are hidden symbols, not public: the reduction and
  recombination programs are `fmpz_multi_mod_t` and `fmpz_multi_CRT_t`, precomputed in
  the constructor with `fmpz_multi_mod_precompute` and `fmpz_multi_CRT_precompute`
  (`/usr/include/flint/fmpz.h:658`, `:689`); the `_precomp` kernel takes the program by
  `const` and writes no state of the context, so a context is immutable after
  construction and safe to share between threads.  The first choice, `fmpz_comb_t`, was
  dropped: its LUTs are built lazily on first use, so two threads reducing against one
  context race (seen with `-fsanitize=thread`); the per-call program is thread-safe.

A context holds `K` (fmpz), `k` (slong), the block array, and the two programs.  The
type is incomplete in the public header.

`test_exports.sh` of lane m1-common would reject new exported symbols, so the two kernels
carry `__attribute__((visibility("hidden")))` on GCC/Clang.  They are still linkable from
the test and the benchmark, which are in the same binary.

First the Python reference `tests/ref/adfref/modctx_ref.py`, then the vectors
`tests/ref/vectors/m1-modctx/modctx.jsonl` (140 records, generated by
`lanes/m1-modctx-b/gen_modctx_vectors.py`), then the C code and the tests
(red-green log in `lanes/m1-modctx-b/tdd-log.md`).  The benchmark is
`bench/bench_modctx.c`, added to `bench/Makefile`.

1. `make -j2 check` -> `check passed: all 14 test programs` (test_modctx: 11 tests,
   10197 checks, 0 failed checks).
2. `make clean && make -j2 check SAN=1` -> `check passed: all 14 test programs`; no
   AddressSanitizer and no LeakSanitizer report.
3. `cc -std=c11 -O2 -g -Wall -Wextra -Wpedantic -Werror -Iinclude -c src/modctx.c` ->
   no output.
4. `./lanes/m1-modctx-b/tsan_modctx.sh` -> the 11 tests pass, 10197 checks, 0 failed,
   and no line contains `ThreadSanitizer` (the script uses `setarch -R` because the
   kernel's ASLR makes ThreadSanitizer abort with `unexpected memory mapping` on a
   plain run).
5. `make mutate FILES=src/modctx.c JOBS=2 LIMIT=150` -> 150 mutants in 493.5 s:
   81 killed, 0 survived, 58 not compiled, 1 timed out, 10 excused in
   `tools/mutate/equivalent.txt`; `mutate: passed`.  Surviving mutants: none.
6. `./bench/bench_modctx --run --trials 15 --cpu 2`, result
   `bench/results/2026-09-28T095515Z_modctx.txt`:
   - `modctx_reduce_4096_128`, call rate: min 27215.3, median 28362.9, max 34425.2
     ns/op.
   - `modctx_recombine_4096_128`, call rate: min 18077.8, median 22050.1, max
     30545.8 ns/op.
   The rows are provisional.  The I/O floor of `docs/PERF.md` section 4 for
   `n = 4096`, `k = 128` is 16 cycles per conversion (section 4 example), so the
   measured internal kernels are far above it: each call does `_fmpz_vec_init` of
   `k` fmpz (an allocation) and a `fmpz_multi_mod_precomp`/`fmpz_multi_CRT_precomp`
   over that vector.  A public kernel that keeps a per-thread scratch or uses
   `fmpz_comb` with a persistent temp would be much faster; the numbers are the cost
   of the thread-safe but allocating internal kernel, not of FLINT's algorithms.
   `quiet_machine: no` (other lanes share the laptop), so the numbers are a harness
   probe, not a machine figure.

Ground truth for the FLINT calls: `fmpz_multi_mod_t`, `fmpz_multi_CRT_t`, their
`precompute` and `precomp` functions are in `/usr/include/flint/fmpz.h:625-692`;
`n_is_prime` and `n_nextprime` are `refs/src/flint-3.0.1/ulong_extras.rst:833` and
`:688` and `/usr/include/flint/ulong_extras.h:335` and `:345`.  The used functions are
the ones the brief names (`fmpz_multi_mod`, `fmpz_multi_CRT`); the `_precomp` forms
are the thread-safe variants of the same programs.

## Findings against the specification

1. **`adf_modctx_new_primorial_pow` has unbounded work and no status to refuse it.**
   Raw context constructors may return only `OK`, `DOMAIN` and `UNSUPPORTED` (3.2,
   closure C3), and conventions 5.14 gives no size limit.  For `e = 1` no block
   overflows, so `n = 2^63` asks for `pi(2^63)` blocks before any status can be
   returned.  I implemented the straightforward loop and note the hole; a later version
   needs a `LIMIT`/`UNSUPPORTED` rule or a stated precondition on `n`.
2. **`adf_modctx_new_from_dump` handles only the `modctx` body (HEADER-FINDING).**
   The header says it returns the context of the occurrence-th context occurrence of
   *any* dump, which includes the contexts nested in `fball l`, `scaled`, `adele`,
   `cadele` and `qclass` occurrences (10.1, 10.2).  The brief restricts this lane to
   the body `modctx`, so the function returns `ADF_PARSE` for any other body, even a
   valid one with contexts.  The nested bodies should be handled by the dump loaders
   of lane m1-text; if the orchestrator wants this function to do it, it needs the full
   grammar.  Marked `HEADER-FINDING` in the code.
3. **A context with `k = 0` and `K` not 1 and below 2^64 is accepted by the dump
   predicate but is not made by any public constructor.**  The reference `_v_ctx` of
   `proto/text_grammar.py` accepts it (it checks `K >= 1` and, only for `k >= 1`, the
   blocks), so `adf1 Q modctx 6 0` is valid and must round-trip byte for byte.  This is
   implemented (an internal raw allocator), but the only public constructor that gives
   `k = 0` is `adf_modctx_new_fmpz`, and it gives `k = 0` only for `K = 1` or
   `K >= 2^64`.  So such a context is reachable only through a dump.
4. **The context duplicates the reduction/recombination programs that lane m1-local
   was told not to use.**  `lanes/m1-local/brief.md` says to use the public read access
   and not to add an internal accessor.  The context therefore precomputes tables that
   the local backend will not read, and m1-local must precompute its own; the mutation
   run and the benchmark pay for both.  Not a contradiction, but an avoidable cost.
5. **The forbidden-byte check `s[i] < 0x20 || s[i] > 0x7e` is redundant with the
   grammar for the dump.**  A byte it would reject (a control byte or a byte >= 0x80)
   also fails `adf_dump_h` or the fixed keyword checks, so the status is `ADF_PARSE`
   either way.  Kept for the stage order of 8.5 and because the value form needs the
   same check; two mutants of the `||` are excused for this reason.
6. **The excused mutants are not all equivalent.**  Two of the ten entries in
   `tools/mutate/equivalent.txt` (`src/modctx.c:698:logic`, `:710:logic`) are
   out-of-bounds reads that `-O2` removes by using the undefined behaviour; the compiled
   mutant gives the same `ADF_PARSE` on the page test, but the source is wrong.  The
   reason there says so.  The other eight are genuinely equivalent or dead code; each
   reason in the file names why.  This is reported rather than hidden because the
   mutation run's `-O2` is what makes the two survive.
